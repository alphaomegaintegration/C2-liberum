CSUTLDTC COBOL -> Java Validated Wrapper Conversion

What this prototype shows: the actual CSUTLDTC COBOL wrapper converted into Java, with traceable mappings for inputs, CEEDAYS invocation, feedback-code interpretation, result fields, and return-code propagation. The CEEDAYS date engine itself is shown as a runtime dependency boundary in the attached target code.

Why the Java file name differs from the COBOL source: this is not a direct file-for-file transpilation from CSUTLDTC.cbl into CSUTLDTC.java. CodeIntent extracts the operational intent of the COBOL wrapper — inputs, CEEDAYS invocation, feedback-code handling, result construction, and return-code propagation — and recomposes that intent into idiomatic Java.

In this slice, the source behavior is represented as CallToCEEDays.java, with CEEDays.java surfaced as an explicit backend/runtime dependency boundary. The target structure differs because the goal is maintainable Java, not COBOL-shaped Java.

Review Boundaries

The prototype surfaces unresolved or environment-dependent issues rather than hiding them.

Boundary 1 - CEEDAYS runtime dependency

Open dependency

Observed in actual target: CEEDays.call(Args ia) currently sets ia.feedbackCode = new FeedbackCode(0).

Implication: the wrapper conversion is traceable and validated, but complete calendar/date semantics depend on implementing or binding the CEEDAYS runtime.

Recommended action: bind to a production CEEDAYS-equivalent runtime or convert/implement the date engine, then run behavior-level validation.

Boundary 2 - Output byte layout

Review if byte-exact required

Observed: COBOL builds WS-MESSAGE via fixed PIC fields. Java uses String.format(MESSAGE_FMT,...).

Implication: field semantics are preserved for the wrapper; exact byte-for-byte parity should be reviewed if downstream systems depend on exact spacing or label spelling.
